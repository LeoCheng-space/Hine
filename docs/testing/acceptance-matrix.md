## 候選：通知與授權失效驗收案例（待批准）

以下案例補充既有 REQ，依據[共同契約候選小節](../contracts/interface-contract.md#internal-notify-invalidation)與[交付與連線狀態表](../contracts/interface-contract.md#delivery-state-table)。**所有預期結果都是候選驗收條件，待 PM 批准；不是既定政策、實作授權或實測結果。** N18 描述不採 E1 的比較方案，N26 描述採 E1 的主要推薦，不能同時當作現行驗收。其餘案例也只在所依賴的候選行為獲准並整合後生效。符號與測試前提：
- `r` 是撤銷交易取得的失效位置，`T_R` 是它的提交時點，`S` 是 `INVALIDATION_STALE_SECONDS`，`W` 是事件的 `invalidation_position`。
- 通知遺失案例需要能攔截 `publishCommitted` 並丟棄 Redis Pub/Sub 訊息。
- 時間窗口案例需要能控制節點的補齊時點。

前提：採完整 C10 待批准方案；以 `t1/k1/g1` 表示原嘗試／獨立物件鍵／GCS 世代，`t2/k2/g2` 表示 A25 後的新組合，並保留該版本核驗時的中繼世代與中繼資料。這裡的 g1／g2 只是案例符號，不按數值大小判定新舊。

1. **A21 就緒後，原 URL 再 PUT 不同內容。** t1 已就緒且 g1 仍為現存物件，原 URL 未到期；重送帶原簽章僅建立標頭的 PUT。預期 GCS 412，不替換 g1，就緒綁定與中繼資料不變，A22 仍只簽 g1。移除／改標頭也不能變成可覆寫請求；物件若異常消失，另依第 4 項，不得拿重新建立的版本頂替。
2. **A25 建 t2 後，t1 的 PUT 晚到。** A25 已原子切換目前嘗試至 t2/k2；t1 的舊 URL 對 k1 可能成功 200（原先空目標）或回 412（已有物件）。兩者都不能碰 k2、不能完成 t2；舊 A21(t1) 回 CONFLICT。只有目前嘗試 t2 核驗 g2 成功才可就緒；若 t2 已就緒，綁定仍是 g2。這不是要求 A25 能即時撤銷全部舊簽署網址。
3. **首次 PUT 成功但回覆遺失，再 PUT 遇到已存在。** 目前嘗試 t1 首次已建立 g1，但用戶端未收到 200；僅建立（不覆寫既有物件）的重試回 412。用戶端不得直接宣稱就緒，也不得刪物件／去掉前置條件；以 A21(t1) 核驗 g1。類型／大小／`sha256` 符合才提交就緒；不符回 CONFLICT，待處理且仍有權時才用 A25 新鍵值／新目標重傳。若 A21 已提交但回覆也遺失，同嘗試重試只回原就緒綁定。
4. **A21 核驗版本與 A22 交付版本不一致／核驗版本不可取。** A21 核驗的是 g1；即使同一物件鍵後來有 g2，A22 也只能為保存的 g1 與核驗中繼資料簽 URL，不能選最新版本。g1 不可讀、中繼世代不符或依賴查詢失敗時，A22 回 DEPENDENCY_UNAVAILABLE，不發 g2 授權憑證、不改綁就緒。若簽出 URL 後 g1 才遺失，GCS GET 失敗，用戶端不得移除世代改取別版；A21 核驗過程已遭換版時亦不能提交就緒。C10 未批准前不得宣稱這些是已實現保證。
